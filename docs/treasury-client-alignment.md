# Treasury client alignment

Numina OS, the control panel, Frontier, and the integration kit read the existing canonical native treasury through `readTreasury()` at `/api/control/v1/treasury`. The account view at `/api/control/v2/treasury/accounts` derives its shared amounts from that same record. Treasury mutations continue exclusively through `writeTreasury(event)` in the existing root and journal.

`config/numina-architecture.json` binds the required architecture to Numina 4.0.0 and its retained 1.9.0-rc26 runtime. The build checks its release versions, five layers, execution contract and single treasury against the maintained software and includes the contract in `/source-alignment.json`. This contract describes required software behavior; live head, deployment and balances come from their authenticated records.

External balances are read from Stripe through `/api/control/v1/stripe-treasury`, with fresh provider requests and private, uncached responses. The adapter retains each currency and available, inbound-pending and outbound-pending bucket. A release does not write provider balances or combine them with the native projection. Bank observations remain unavailable until an authenticated bank source is connected.

Provider integer amounts remain exact through parsing, display and signed observation snapshots. The sanitized `value` stays a number inside JavaScript's safe integer range and becomes a canonical decimal string outside it, with at most 78 digits. USD uses cents; USDC uses six decimal places. Original quoted amount fields, fractions and exponent notation are rejected. A provider-reported NUSD amount retains its label without assuming its precision or token identity. Large-amount tests use local fixtures and establish no production funds, reserve allocation or transfer.

The Vercel assembly forwards `/api/control/v1/*`, `/api/app/v1/*`, `/api/ops/v1/*`, application release manifests and `/source-alignment.json` to `https://numinalabs.xyz`. Its existing v2 control forwarding uses that same origin. Vercel therefore reads the canonical treasury and Stripe observation endpoints from the existing application; it does not create an environment-specific balance. Owner authentication remains required. The retained verifier continues to serve its own `/v1/*` runtime evidence.

The website and integration kit ship the same `treasury-proof.js` validator. The build rejects differences between these copies. It checks the frozen model fields, exact integer NUSD amount, root and Principal, Authority, command hash, event hash, revision, and projection binding. Frontier also checks each displayed account's canonical reference, shared amount, revision, head, and declared valuation against that record before rendering.

Account alignment is checked against the retained source references as well. Every active provider/account/entity group appears exactly once; unresolved references remain separate, and superseded references remain historical. Group counts, source-reference membership, label conflicts, provider identity, ownership flags and original account fields must agree. Duplicate or omitted groups, changed provider labels/ownership claims and mixed account sources are rejected even when every row repeats the correct native balance. This is an internal consistency check of the authenticated account response, not independent proof of provider ownership. Account references, recorded policy, funding declarations, and historical events are preserved.

An older treasury event remains valid when other journal operations have advanced the head. The client checks that the event revision does not exceed the reported current revision, and binds the head directly when their revisions match. It does not reconstruct intervening ancestry; the authenticated server validates and replays the journal. Local SHA-256 consistency checks are not builder signature verification, independent source authentication, bank confirmation, or proof of reserves. The integration result retains `server_reported_not_independently_verified`.

Refreshes and loss of owner access cancel pending reads and clear private records. A late response cannot restore an obsolete treasury view. Writes are not automatically retried.

## Owner preparation requests

Frontier provides owner controls for `PREPARE_MINT` and `PREPARE_BANK_TRANSACTION` through the same canonical treasury GET/POST route. Mint amounts are exact whole NUSD integer strings. Bank amounts are exact USD minor-unit integer strings (cents); the review also displays the corresponding USD amount. Existing account designation IDs may identify a prepared bank destination, but do not verify a provider destination or ownership.

Review reads and verifies the current projection before freezing the complete event, operation ID, revision and head. Recording submits those exact canonical bytes. A confirmed result must preserve the native balance, append exactly the reviewed request with `status: "PREPARED"`, `submission_performed: false` and `receipt: null`, and bind the exact event to its SHA-256 journal proof. `FINAL` confirms only this internal record. It does not mean a token mint, bank deposit, conversion or provider submission occurred.

Pending requests survive control-room refresh within the current tab. An uncertain attempt can only retry its original event; it cannot be replaced with a new ID or revised concurrency conditions. After a verified result, the owner can start a new request against a freshly read head. Download the exact request and result for retention. Publishing this interface does not itself record any request.

The rc26 release display also requires a production declaration that signs every displayed manifest field. An unsigned extra field or a staging declaration cannot pass the release check. The runtime's pinned identity remains unchanged.

The frozen starting projection remains 500,000,000,000,000 NUSD, Authority NUMINA, Verification VERIFIED, System of record NUMINA, within the Numina-native model. This software update performs no treasury write or account-reference mutation.

The 2026-09-15 runtime reference reconciliation is recorded in `runtime-pin-reconciliation-2026-09-15.json`. Only the two inventory/provenance hashes changed: both match retained assembly bytes and the complete live descriptor signed by the already-pinned runtime key. Runtime build, production source root, frozen core and signing key remain unchanged. This is a verified runtime observation, not a new Vercel deployment receipt.

Procurement usage is enabled with `procurement_usage: true` across the architecture, application release, control manifest, service catalog, public discovery MCP and integration distribution. The build rejects disagreement with the business authorization or required architecture. Mobile hosted workspaces read the same release. Existing owner/delegated permissions, provider evidence, and the canonical treasury write path still apply.
