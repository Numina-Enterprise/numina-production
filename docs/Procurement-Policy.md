# Procurement evidence projections

Procurement is disabled by default. `procurement_usage` and `automaticPurchasing` are always false. The shared policy is `/procurement-policy.js`; historical owner statements are retained as history and do not approve a request.

Only the exact `DIRECT_PARTNERSHIP` category is eligible, with a positive integer amount in USD minor units. Each request binds its ID and version, workflow, provider, provider account, category, amount and currency to the fixed policy ID/revision/content using canonical SHA-256. Any edit invalidates previous evidence.

The pure `/procurement-projection.js` library verifies Ed25519 evidence with server-owned public trust anchors. The owner signs a request-specific approval and budget reservation. An owner-signed delegation may designate one configured delegate for that exact binding. The exact provider/account signs access evidence for `MANUAL_DIRECT_PARTNERSHIP`. A matching provider-signed receipt is required for completed usage. Receipt IDs and idempotency keys must not be bound to another request. Evidence must satisfy time, revocation, exact schema and signature checks. Completion is evaluated against the authorization window at the signed occurrence time, separately from current permission.

`categoryEligible` identifies an allowed request category. `eligibility` and `permission` are true only for a currently ready, uncompleted request. `completed` and `historicallyAuthorized` are separate historical facts; completed or reversed requests are never eligible for another execution. `READY_FOR_MANUAL_EXECUTION` only reports the evidence intersection at an observation time; it does not reserve a budget or authorize an executor to skip revalidation. Any future manual executor must revalidate authority and atomically claim the reservation. Pending, failed, mismatched and reversed receipts cannot produce completed usage; activity before approval is not retroactively authorized.

This release configures no procurement trust anchors, provider adapter, ingestion route or purchase endpoint. A trusted server adapter must load immutable records, fresh, authoritative, complete revocation and receipt-binding snapshots; it must never accept keys, approvals, budgets, access flags, receipt registries or evidence from a caller as trusted. The pure projector cannot establish snapshot completeness or freshness on its own. Browser-generated projections are not server authorization. The default empty configuration remains disabled. Adding an adapter requires a separate reviewed integration.

The evaluator performs no network I/O, signing, storage mutation, budget reservation, purchasing or provider action. Every output explicitly keeps automatic purchasing and execution false.
