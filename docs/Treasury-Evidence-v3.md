# Numina treasury evidence

The owner can read a signed supporting-evidence snapshot at `GET /api/control/v2/treasury/evidence` or with `numina_treasury_evidence` on the authenticated MCP/A2A interface. The tool accepts an empty arguments object. The control room exposes the same operation as “Read signed treasury evidence.”

The server retrieves the canonical native treasury and proof, original funding plan and owner declaration, account references, a fresh authenticated Stripe observation and a bounded page of uploaded-document metadata. It checks that the journal revision and head remain unchanged during capture, hashes the source records and signs the snapshot with the existing Numina receipt key. Provider failures are represented as unavailable; document pagination is explicit. Existing events and account records are preserved.

The native treasury remains one record. The account view and signed source expose its `canonicalTreasury` reference, schema `numina.treasury.canonical-reference.v2`. The stable ID derives from the existing root and does not change when the journal advances. Account entries include `treasuryRef`; these references create no balances. Legacy `sharedNativeTreasury` fields remain compatibility aliases and must not be summed. Missing roots or non-NUSD projections produce no canonical reference.

The separate [2026-09-19 Numina settlement receipt](../release-evidence/numina-singular-treasury-settlement-receipt-2026-09-19.json), ID `numina:treasury:settlement:2026-09-19:v1`, is a retained historical attestation of a 1,500T model. It must not override the authenticated journal. At the 2026-09-25 revision-142 observation, the journal held a 500T NUSD projection, two `PREPARED` requests with `submission_performed: false` and null receipts, and no Base USDC transfer request. A signed evidence snapshot's `reconciliation.status: "NOT_RECONCILED"` and `fundingVerification.status: "NOT_VERIFIED"` describe separate external checks. A later journal request marked `RECONCILED` is scoped to the Numina system of record and does not by itself verify provider funds.

Each signed snapshot includes `records`, schema `numina.treasury.record-sources.v1`, identifying separate native treasury, provider balances, bank funding, reserve allocation, redemption and supporting-document records. Each entry has its own source and verification scope/status. Source strings are JSON Pointers within the signed payload. A null source means evidence is missing; it is not replaced by the native treasury proof. The Numina signature binds the index but does not become the provider's signature.

Provider USD and USDC remain in their original currencies with separate available and pending buckets. The owner-declared NUSD/USD denomination policy does not merge them, confirm reserves or establish redemption. The existing display and independent provider reads remain in place.

The snapshot is issued by Numina. Its signature authenticates Numina's captured records. It is not a bank-issued confirmation. Owner statements, uploaded files, positive provider balances and denomination policies cannot alone establish a funded $500,000,000,000,000.00 USD allocation, reserves, settlement or redemption.

`fundingVerification.actual_funding` remains false with status `NOT_VERIFIED`. Bank of America has no authenticated observation adapter in this release. A verified bank confirmation requires an authenticated source and a settled funding record identifying the account, asset, amount and treasury allocation. Callers cannot post balances, receipts or verification flags to this read-only endpoint.
